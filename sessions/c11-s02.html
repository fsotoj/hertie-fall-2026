R4DS 25 — three kinds of function, not one

The chapter's organising move is that "write a function" means three different jobs in R, and each has its own trap.

The trigger for writing one at all is repetition: copy and paste a block more than twice and it should have been a function. The payoff the chapter argues for is not brevity but correctness — a fix applied in one place rather than in every copy you made.

Vector functions take one or more vectors and return a vector. These behave the way functions do in most languages, and they are the straightforward case.

Data frame functions are where R stops behaving like other languages. Passing a column name into a function does not work naively, because tidyverse verbs use data masking: they evaluate bare column names inside the data frame. The chapter's answer is embracing, wrapping an argument in {{ }} so the function passes the expression through rather than evaluating it too early. If one idea from this session shows up in your homework, it is this one.

Plot functions are the same problem again in ggplot2, where aes() does the data masking. The chapter closes on style: naming, and why a function's name should be a verb describing what it does.

Advanced R 22 — a strategy first, then the tools

The learning objective phrases it in that order deliberately: the general approach matters more than knowing which function to call.

The four steps, in the chapter's own order. Google the error message, with the variable-specific parts stripped out. Make it repeatable, which means reducing it to a minimal reproducible example. Figure out where it is, by forming hypotheses and testing them one at a time rather than changing things at random. Then fix it and test it, to confirm both that the bug is gone and that you have not introduced another.

The middle step is the one people skip. Reducing a failure to the smallest case that still fails usually identifies the cause on its own, before any debugger is opened.

The tools, grouped by what they are for. Locating an error: traceback() for the call sequence that led to it. Stopping inside a running function: browser(), RStudio breakpoints, debug() and debugonce(), trace() for inserting code at a chosen point, and options(error = recover) to land in any frame after a failure. For code that is not running interactively, dump.frames(). The chapter also covers non-error failures, where nothing crashes but the answer is wrong, which is the harder category and the one that matters most in data analysis.

What you should be able to do afterwards

  • Say when a repeated block should become a function, and why
  • Write a function that takes a column name as an argument, using {{ }}
  • Explain what data masking is and why it makes data frame functions awkward
  • Reduce a failing script to a minimal reproducible example
  • Choose between traceback(), browser() and debugonce() for a given failure
  • Debug a wrong answer, not just a crash
